# Стиль кода

Этот документ определяет соглашения для TypeScript и React. Архитектурные границы описаны в
[architecture.md](architecture.md), правила интерфейса и CSS — в [ui.md](ui.md), тестов — в
[testing.md](testing.md).

## Автоматические проверки

- `npm run format` форматирует проект с помощью Prettier.
- `npm run format:check` проверяет форматирование без изменения файлов.
- `npm run lint` запускает ESLint, включая type-aware правила TypeScript и проверку направления
  импортов между слоями.
- Lefthook перед commit форматирует staged-файлы и проверяет staged TypeScript-файлы ESLint. Перед
  push запускаются полные проверки форматирования, ESLint и сборки.
- Не отключать правило для файла или блока, если проблему можно исправить локально. Точечное
  отключение сопровождается кратким объяснением причины.

Форматирование не обсуждается в review: источник истины — конфигурация Prettier. Ручные переносы,
которые форматтер удаляет, не сохранять искусственно.

## Имена и файлы

- Компоненты и их файлы — `PascalCase`: `ObservationCard.tsx`.
- Функции, переменные и hooks — `camelCase`: `useObservations`.
- Boolean-значения начинаются с `is`, `has`, `can` или `should`.
- Обработчик внутри компонента называется `handle…`, callback в props — `on…`.
- Имя отражает доменное назначение. Не использовать неинформативные `data`, `item`, `value`, если
  доступно более точное имя.
- Тесты размещать рядом с проверяемым модулем; один основной компонент обычно соответствует одному
  файлу.

Не дробить код только ради размера файла. Локальный компонент или helper остаётся рядом с местом
использования, пока у него нет самостоятельной ответственности или повторного использования.

## Импорты и экспорты

- Использовать именованные экспорты. Default export допустим в точках интеграции, где он ожидается
  инструментом или выбранным API.
- `import type` использовать, когда импорт нужен только системе типов.
- Публичный `index.ts` создавать на границе модуля, а не в каждой папке.
- Импортировать модуль через его публичный API. Не обращаться к приватным внутренним файлам другого
  модуля.
- Соблюдать направление `app → pages → widgets → features → entities → shared`. Обратные зависимости
  запрещены и проверяются ESLint.

## TypeScript

- `type` использовать по умолчанию. `interface` применять, когда контракт намеренно расширяется или
  участвует в declaration merging.
- Не использовать `any`. Для неизвестных внешних данных использовать `unknown` и выполнять проверку
  либо валидацию.
- Не скрывать ошибки через необоснованные type assertions, non-null assertions, `@ts-ignore` или
  отключение правил.
- Предпочитать discriminated unions независимым boolean-флагам для взаимоисключающих состояний.
- Полагаться на inference для очевидных локальных значений; явно типизировать публичные контракты и
  места, где тип уточняет намерение.
- Не вводить `enum`, если достаточно union литералов или объекта `as const`.
- Обрабатывать невозможные состояния явно; при необходимости использовать exhaustive check.

## React

- Props типизировать непосредственно; не использовать `React.FC` без конкретной необходимости.
- Hooks вызывать в начале компонента и группировать по ответственности.
- Сначала обрабатывать состояния, допускающие early return, затем формировать основной JSX.
- Сложное условие давать именованной переменной или функции вместо вложенных тернарных выражений.
- Не применять `useMemo` и `useCallback` профилактически. Добавлять их при измеримой пользе или когда
  стабильность ссылки является частью контракта.
- Не создавать эффект для значения, которое можно вычислить во время render.
- Состояние хранить у ближайшего владельца; не копировать props или server state в локальный state без
  необходимости.
- Пользовательский текст получать через `t(...)`, а не размещать строковым литералом в JSX.

## JSX и доступность

- Использовать семантический HTML. Интерактивное действие реализовывать через `button`, `a`, `input`
  и другие подходящие элементы, а не через `div` с `onClick`.
- Интерактивный элемент должен иметь доступное имя и работать с клавиатуры.
- Связывать поля формы с label и сообщениями об ошибках; не использовать placeholder как единственную
  подпись.
- Декоративные изображения и иконки скрывать от accessibility tree, информативным задавать текстовую
  альтернативу.
- Управлять фокусом в dialog, overlay и bottom sheet согласно правилам из `ui.md`.

Автоматическая JSX-проверка доступности будет добавлена после появления версии
`eslint-plugin-jsx-a11y`, совместимой с используемым ESLint 10. До этого требования проверяются при
review и UI-тестировании.

## CSS

- Локальные стили хранить в CSS Module рядом с компонентом; глобальные стили оставлять минимальными.
- Класс называть по роли элемента: `header`, `animalName`, `isSelected`. Не переносить BEM поверх CSS
  Modules.
- Повторяющиеся значения брать из CSS Custom Properties. Новый token добавлять только при реальном
  повторном использовании или системной роли.
- Inline styles использовать только для динамических значений, которым не подходит class или CSS
  Custom Property.
- Не использовать `!important` без объяснимой причины.
