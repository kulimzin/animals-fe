# Архитектура

## Ответственность слоёв

| Слой       | Ответственность                                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------------------------------ |
| `app`      | App, общие providers, маршрутизация, оболочка страниц, глобальная конфигурация, стили и tokens                     |
| `pages`    | Композиция самостоятельных страниц, связь событий, состояние нескольких частей страницы                            |
| `widgets`  | Крупные блоки: Header, Map, MapFilterPanel, MapOverlays                                                            |
| `features` | Законченные действия: выбор животных/периода/местоположения, просмотр/добавление встречи, голосование, смена языка |
| `entities` | Animal и Observation: типы, модели, доменные запросы и ключи кэша, преобразования, форматирование, UI сущности     |
| `shared`   | Независимые от сценариев api, ui, lib, config, i18n и assets                                                       |

Не создавать слой или feature только ради группировки файлов. Страница координирует сценарии; их бизнес-логика остаётся в features и entities. Страницы не импортируют другие страницы.

`shared` не зависит от продуктовых слоёв. Простые UI-примитивы не относятся к widgets. Не создавать сущности без соответствующего доменного понятия.

## Страницы и маршрутизация

Основная страница — `MapPage` в `pages/map`. Её композиция не относится к `App`.

```text
App
├── Общие providers
└── Текущая страница
    └── MapPage
        ├── Map
        │   ├── ObservationLayer
        │   ├── ClusterLayer
        │   └── MapControls
        ├── MapFilterPanel
        └── MapOverlays
            ├── AnimalSelector
            ├── ObservationDetails
            ├── AddObservation
            └── Success
```

Общий Header размещать в оболочке, если он одинаков для всех страниц; управление картой оставлять внутри MapPage.

Для одной страницы App может отображать MapPage напрямую. При появлении второй самостоятельной страницы добавить маршрутизацию в app, выбрав router под реальные маршруты.

Не создавать страницы для overlay. URL встречи может открывать overlay карты.

Восстановление фильтров и положения карты при возвращении определять отдельным требованием к состоянию. Постоянное монтирование MapLibre для этого не обязательно.

## Состояние

Размещать состояние ближе к владельцу:

- Server state: TanStack Query, общий provider в app. Животные, встречи, создание и голосование используют query/mutation; не копировать данные Query в Context или store.
- Form state: React Hook Form и Zod; соответствующий resolver при необходимости. Не создавать собственную form-state систему поверх них.
- UI state: React state. Фильтры и overlay карты принадлежат модели MapPage; локальные состояния — самим компонентам.
- Context использовать, если состояние нужно нескольким удалённым компонентам дерева. Не вводить глобальный store ради нескольких props.

Взаимоисключающие overlay карты моделировать единым discriminated union:

```ts
type OverlayState =
  | { type: 'none' }
  | { type: 'animal-selector' }
  | { type: 'observation'; observationId: string }
  | { type: 'add-observation' }
  | { type: 'success'; observationId: string }
```

Не заменять его независимыми boolean. Другие страницы управляют overlay независимо; общий менеджер добавлять только по реальной необходимости.

Если параметры нужны для ссылок или навигации браузера, хранить их в URL. URL становится источником соответствующего состояния, без независимой копии в React state.

## MapLibre

Прямую работу с MapLibre API изолировать внутри map-модуля. Не распространять instance и вызовы addSource/addLayer/flyTo/fitBounds по приложению.

Внешнее управление предоставлять небольшим интерфейсом необходимых операций. Features взаимодействуют с картой через события и композицию страницы, без импорта map-widget.

Для большого количества встреч использовать:

```text
Observation[] → GeoJSON FeatureCollection → MapLibre Source → Layers/clustering
```

Не создавать отдельный React DOM-marker для каждой встречи. React отвечает за application UI, MapLibre — за географические объекты и clustering.

При клике карта передаёт observationId странице, которая открывает overlay. Marker не управляет карточкой самостоятельно.

Фильтры включать в параметры запросов и query key. Если данные зависят от viewport, обновлять их после завершённого значимого изменения, например moveend, а не на каждом событии движения.

## API и типы

- Сетевую работу отделять от UI; не писать произвольные fetch в presentation-компонентах.
- Общий HTTP-клиент и обработку сетевых ошибок размещать в shared/api; доменные запросы — в entities; сетевую логику действий можно размещать в features.
- При наличии OpenAPI рассмотреть генерацию типов и клиента. Не создавать frontend-типы, противоречащие backend contract.
- Использовать domain types, discriminated unions, inference для очевидных типов и unknown для неизвестных внешних данных.
- Не подавлять ошибки TypeScript без объяснимой причины.
- Имена отражают назначение: observation, selectedAnimalIds, openObservation. Boolean: is/has/can/should; компоненты: PascalCase; hooks: use.
